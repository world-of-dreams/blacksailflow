## 核心

任务群是一条长期存在的领域/职能线。一个 mate 长期负责一个群，跨很多版本、做上千轮都正常。
群会休眠：这段时间没有它的事，就停在那里；下次需要时唤醒同一个 mate 接着做。休眠是等下一次唤醒，不是用完即弃，也不是归档封存。

切群是为了把工作摊开、并行推进、缩短总时间。

## 怎么切

先列这个系统里长期由同一人负责、能独立推进的领域/职能线，一条线一群；群的数量跟着线走，不先定数字。

按实际职能核对每一条线：是不是跨版本一直在，有没有自己的产出与验收，和别的线是不是只靠少数接口打交道。拿不准某条线该不该独立成群，直接问用户。

不按文件分布、验收命令、建设时长、工程阶段（设计/实现/测试/发布）切。这些不是长期职责线：按文件或命令切，同一片责任会被拆碎；按阶段切，等于按时间给同一批人派活，版本一翻就要重来。也不要拿「太大 / 太小 / 两小时能做完」量群——群不是按这一版的工作量划的。

示例（示意，换成你项目自己的职能线，不照抄）：

- 一个文档站：写作 / 站点构建 / 搜索 / 部署。
- 一个硬件产品：结构 / 电路 / 固件 / 认证。

列完按实际职责再核一遍：能由同一个 mate 推进的线并在一起，一条线里混着两种长期职责就拆开。

## 交界

群与群之间定契约：接口、数据结构、文件格式、版本约定。契约记进任务表，不只在对话里说。

## 负载

某个 mate 这段时间活多，通常只是用户最近更关心它那条线，不代表群切错了，也不代表这个群比别的大。
把失衡的事实报给用户：谁忙、忙在哪、持续多久；是否重新切群由用户决定，不自行重切。

## 什么时候会用到别的 skill

- 群和契约定好、要交给 mate 长期负责 → **bsf-commission**。
